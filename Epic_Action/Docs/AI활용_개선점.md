# AI 활용 개선점 (AX 관점)

무기 아바타 씬 작업 대화(2026-10-30)를 돌아보고 정리했다.
목표: 사람은 방향과 판단을, AI는 구현과 반복을 맡아 같은 시간에 더 많이, 덜 되돌아가며 만드는 것.

## 1. 잘 된 것 — 계속 쓸 것
| 방식 | 효과 |
|---|---|
| 설계 먼저(design-first) → 질문을 한 번에 모아 받고, 질문마다 추천 기본값을 붙임 | "추천대로" 한마디로 결정이 끝났다. 결정 왕복이 1~2회로 줄었다 |
| 요청을 번호 목록으로 다시 말하고 확인받기 | 1타/2타 범위, 일반 가위 제거 범위 같은 오해를 구현 전에 잡았다 |
| 파일 단위로 소유권을 나눠 병렬 워커 실행(전기톱 ↔ 가위 ↔ 총) | 충돌 없이 동시에 진행됐다 |
| 핵심 구조(베이스 클래스·예시 1개)는 메인이 직접 쓰고, 반복 구현만 위임 | 워커 결과물의 스타일과 API가 일관됐다 |
| 플레이해 본 뒤의 구체적 피드백("1타가 정면을 못 벤다", "갑자기 공중부양") | 가장 큰 품질 향상은 이 피드백에서 나왔다. AI는 플레이를 못 하므로 이 단계는 사람 몫 |
| 모호한 요청에 해석을 되묻기("쏘는 총이 넉백": 적이 밀리는 것인가 총이 밀리는 것인가) | 한 번의 선택지로 정리돼 잘못된 구현을 막았다 |
| 모델의 정점 데이터를 직접 읽어 가늠좌 정렬을 검증(조준환 중심 0.199 vs 가늠쇠 끝 0.2455 → 5.85° 기울기) | "가늠좌가 이상하면 알맞은 화면을 만들어 달라"는 요청에 추측이 아니라 수치로 보정 방향을 정했다 |
| 구조가 바뀌는 기능은 Plan 모드로 설계 먼저(가늠좌 조준), 질문마다 추천값 | 사람이 "추천대로"로 3개 결정을 한 번에 끝냈다 |

## 2. 시간을 잃은 지점과 원인
| 사건 | 손실 | 원인 | 다음부터 |
|---|---|---|---|
| Codex 워커가 `orca`를 못 찾고 멈춤 | 왕복 2회, 약 15분 | 워커 터미널 PATH에 orca 없음 | PATH에 Orca bin 폴더 추가. 그 전까지는 작업 지시에 절대경로 포함 |
| Haiku 서브에이전트가 개인 지침(수정 전 사용자 확인)을 이유로 수정 거부 | 왕복 1회 | 승인된 계획도 서브에이전트에게는 "사용자 확인"이 아님 | 개인 CLAUDE.md에 예외 추가: "사용자가 승인한 계획 범위 안에서 위임받은 서브에이전트·워커는 확인 없이 수정한다" |
| "4번 누르면 총이 안 나옴" | 왕복 1회 | 코드·데이터를 바꾼 뒤 씬 빌더를 다시 실행하지 않음 | AI는 데이터 변경 직후 빌더 재실행까지 한 단위로 처리. 사람은 "빌더 다시 돌렸는지"를 먼저 확인 |
| 수치·포즈를 실행 없이 추정 | 전기톱 3번 반복 | 모델 방향·크기와 손맛은 코드만으로 판단 불가 | 첫 구현 후 바로 짧게 플레이해 보고, 가능하면 스크린샷이나 영상과 함께 피드백 |
| 대화가 길어짐 | 컨텍스트 압박 | 한 세션에 기능 여러 개 | 기능 단위로 진행사항.md를 갱신하고 /clear |
| "1타 똑같은데?" (전기톱 1타 수정 후) | 왕복 2회 | 빌더 코드만 고치고 데이터 에셋이 갱신됐는지 확인하지 않은 채 "수정 완료"로 보고 | 데이터가 걸린 변경은 에셋 파일의 값(`bodyYaw`, `leap`)과 수정 시각까지 확인한 뒤 보고한다 |
| 재빌드 메뉴를 실행했는데 반영되지 않음(3회) | 왕복 3회 이상, 사람이 자리를 비운 사이 지연 | 열린 씬이 수정 상태면 저장 확인 창에서 멈춘다. 게다가 `invoke_menu`는 멈춤·예외와 관계없이 success를 돌려준다 | 메뉴 실행 결과를 믿지 말고 에셋 수정 시각·값으로 확인한다. 안 바뀌었으면 "창이 떴을 수 있다"고 바로 알린다 |
| 총 가늠좌 코드를 짜고도 빌더가 예외로 중단됨 | 미해결(데이터 없이 보고) | 모델이 OBJ 1개 렌더러로 합쳐져 들어오는데, 이름으로 파트를 찾는 코드를 실행해 보기 전에 확정함 | 모델 구조를 가정하는 코드는 짜기 전에 임포트 결과(렌더러 목록)를 먼저 확인한다. `eval`로 1회 조회하면 된다 |
| "박차는 게 안 보임" 원인을 코드만 읽고 추정 | 왕복 1회 | 도약 로직은 맞는데 "웅크림 → 튀어오름" 준비 동작이 없어 안 보인다는 가설만 세움. 사람의 "약간만 뜸" 답을 받고서야 높이를 올림 | 가설을 말하더라도 먼저 사람에게 "뜨기는 하나요?"처럼 현상을 확인하는 한 가지 질문을 던진다 |
| 내부 용어가 전달되지 않음("공격포즈?") | 왕복 1회 | 질문에 `leap`, `Motion`, `SaveCurrentModified…` 같은 코드 용어를 그대로 씀 | 사람이 정할 일은 화면에서 보이는 말로 쓰고, 코드 용어는 괄호 안에 둔다 |

## 3. 요청을 이렇게 하면 더 빨라진다
1. **무엇이 이상한지 + 어떻게 되길 원하는지 + 어디까지**를 한 번에 쓴다.
   - 예: "전기톱 1타(대각선 회전)가 정면 적을 못 벤다. 회전 중간에 정면을 지나가게. 다른 타는 그대로."
2. 기준이 되는 예시를 준다. 레퍼런스 게임, 영상, 그림, "○○처럼". 이동·타격감은 말보다 예시가 정확하다.
3. 우선순위와 범위를 명시한다. "이번엔 전기톱만, 총은 다음에"처럼 쓰면 병렬화와 확인 범위가 명확해진다.
4. 결정을 위임할 때는 "추천대로"를 적극적으로 쓰되, 바꾸고 싶은 항목만 집어서 고친다. 이번 대화에서 효과가 컸다.
5. 모델·effort를 고르는 기준(이번 경험)
   - 구조 설계와 통합: 메인(Opus)
   - 패턴이 정해진 다수 파일 구현: Sonnet 또는 Codex medium
   - 기계적인 수정: Haiku. 단, 위 개인 지침 예외를 넣어야 실제로 일한다
   - 수치 조정이나 작은 동작 수정: Codex low

## 4. AX 워크플로 제안 (다음 작업부터 적용)
```
요청(무엇·왜·범위)
 → AI: 요구사항 재정리 + 설계 + 질문(추천값 포함)
 → 사람: "추천대로" 또는 항목별 수정 = 승인
 → AI: 핵심 구조 직접 구현 → 반복 구현은 워커에 파일 소유권 단위로 병렬 위임
 → AI: 통합·컴파일·빌더 재실행까지 완료
 → 사람: 짧게 플레이 → 구체적 피드백(무엇이·어떻게 이상한지)
 → 반복
 → 기능 단위 마무리 때 진행사항.md 갱신 + 블로그 소재 메모 → /clear
```
- 측정해 볼 것: 요청 1건당 왕복 횟수, 워커 대기(유휴) 시간, 플레이 피드백 반영 횟수. 이 세 개가 줄면 AX가 진전된 것
